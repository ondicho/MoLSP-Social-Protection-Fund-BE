# Technical debt and known gaps

This prototype was delivered within the 8-hour assessment time-box. Data
integrity, workflow correctness, security and tests took priority over feature
volume. The items below are known, deliberate gaps, each with its risk and a
recommended next step.

| # | Area | Gap | Risk | Recommended next step |
|---|---|---|---|---|
| 1 | Data seeding | Only geography, lookup values and one bootstrap platform admin are seeded. There are no curated fund or anonymised demo datasets. | New environments start empty; behaviour at realistic volumes is untested. | Agree an authoritative seed set with MoLSP. Add environment-gated seed migrations and an anonymised demo dataset. |
| 2 | Validated geography | Counties and sub-counties use a provisional catalogue. Wards are matched to sub-counties by exact name, so some constituency groups stay unmatched (see [GEOGRAPHY.md](GEOGRAPHY.md)). Location, sub-location and village are validated free text, not integer-keyed lookups. | Misattributed or inconsistent locations weaken targeting, reporting and county fund restrictions. | Obtain the official IEBC/KNBS hierarchy from the Ministry. Load County > Sub-county > Location > Sub-location > Village as integer-keyed tables with a reconciliation report. |
| 3 | Data gaps | Applicants have no email field, so notifications are SMS only. Household, income and vulnerability indicators are not captured. | Applicants without phones cannot be reached; there is no objective data for eligibility (see item 6). | Confirm the data dictionary with the Secretariat. Extend the form and add an email channel to the existing outbox. |
| 4 | Identity verification | ID or passport numbers are checked only for format (alphanumeric, max 20) and uniqueness. There is no IPRS or Maisha Namba lookup. | Fraudulent applications using fabricated, borrowed or deceased persons' identities. A fraudster can also register a real person's ID first and block their genuine application. | Integrate IPRS behind a verification interface. Store verification status and match score, and block approval of unverified applicants. |
| 5 | Contact verification | Phone numbers are normalised to E.164 and unique, but ownership is not proven. OTP and email magic-link verification were not built because of time constraints. | Fake or third-party numbers, misdirected notifications and scripted public self-registrations. | Add phone OTP and email magic-link verification before submission, plus rate limiting and CAPTCHA on public endpoints. |
| 6 | Approval criteria | Approval is a manual approver decision. There is no eligibility matrix, vulnerability scorecard, means test or credit/income scoring. | Inconsistent, subjective decisions that are hard to audit or defend. | Model a configurable, versioned scorecard per fund (criteria, weights, thresholds). Calculate and store the score with the application, and require a justification for overrides. |
| 7 | County fund pre-validation | Intake checks only that the selected fund slug exists and is not archived. It does not enforce county coverage for county-restricted funds, the fund's open/close window, or amount limits (time constraint). | Ineligible applications are accepted and approved; funds can leak across counties. | Enforce fund type, counties and date window on create, submit and approve, with field-level 400 errors. Filter fund options by the selected sub-county in the UI. |
| 8 | Correction and resubmission | Applications returned for correction are locked. There is no amend/resubmit endpoint; the `RESUBMITTED` audit event is reserved for it. | Returned applicants cannot complete their application, and the duplicate-ID rule blocks re-applying. | Let the creator amend `RETURNED_FOR_CORRECTION` records and resubmit to `SUBMITTED`, with audit and notification. |
| 9 | Notification delivery | Delivery is at-least-once because the SMS provider has no idempotency key. There are no delivery-receipt webhooks and no re-queue for `FAILED` messages. | A rare duplicate SMS after a crash; failed messages need manual database intervention. | Pass the outbox ID as a provider idempotency key where supported. Add receipt webhooks and an audited admin re-queue endpoint. |
| 10 | Production hardening | Audit immutability relies on the application having no update/delete path plus documented database grants, not triggers. There is no password reset, MFA or account lockout. | Audit tampering if grants are not applied; account-takeover exposure. | Restrict audit tables to `SELECT, INSERT` grants. Add password reset, MFA for approvers and admins, lockout, and a secrets vault. |
